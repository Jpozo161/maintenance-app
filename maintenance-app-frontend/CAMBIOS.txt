ARCHIVOS QUE NECESITAN LA API

src/services/api.js
Es el cliente compartido para GET y POST. Consulta las rutas centralizadas en src/data/modules.js y también GET /residenciales. Envía POST a /register, /pagos y /maintenance.

src/data/modules.js
Define las rutas GET /propietarios, /pagos, /mantenimiento, /novedades y /nextmaintenance. También normaliza los datos recibidos.

src/components/Dashboard.jsx
Consulta mediante getResource los cinco recursos del inicio: propietarios, pagos, mantenimiento, novedades y próximos mantenimientos.

src/components/MaintenanceModule.jsx
Consulta los registros del módulo seleccionado: propietarios, pagos o mantenimiento.

src/components/form.jsx
Consulta GET /residenciales para el selector y envía registros mediante POST a /register, /pagos o /maintenance.

src/components/Sidebar.jsx no hace peticiones API. Obtiene nombres e íconos de src/data/modules.js.

src/components/FailureReport.jsx todavía no guarda datos en la API; actualmente solo muestra una confirmación local.

src/components/OcrComparison.jsx envía los archivos a POST /ocr; la extracción se implementa en el servicio del backend.


CONFIGURACIÓN DE API Y CORS

En desarrollo, vite.config.js reenvía las solicitudes /api/* a http://localhost:3000/*. El navegador consulta el mismo origen del frontend y Vite las transmite al backend, lo que evita el bloqueo CORS en esas peticiones.

El backend debe estar activo, exponer las rutas anteriores y responder JSON. Si VITE_API_URL se configura con una dirección absoluta, la llamada vuelve a ser entre orígenes y el backend debe autorizar el origen del frontend mediante CORS.

Las propiedades que entrega el backend deben corresponder con los campos que transforma toTableRows en src/data/modules.js.


VERIFICACIÓN

npm run lint y npm run build: correctos. Se verificó GET /pagos con identificadores y POST /ocr con una imagen de factura; se extrajeron emisor, número, fecha y total.

10. Formato de fechas

Se centralizó formatDate en src/data/modules.js para mostrar fechas como DD/MM/YYYY en la zona America/Bogota. Se aplica a pagos, mantenimientos, averías, próximos mantenimientos y pagos recientes del Dashboard. Los valores vacíos o no válidos se muestran como guion.

11. Menús, filtros y OCR funcional

DataTable centraliza búsqueda, filtro y paginación. Usuarios, Propiedades y Pagos tienen menú de tres puntos por fila con Editar y Eliminar; los usuarios cargan su rol desde la tabla roles y editan el rol con opciones obtenidas de GET /roles. Se quitó Estado de las tablas Usuarios y Propiedades. Los pagos y usuarios tienen rutas PUT/DELETE por ID. El OCR está en el servicio del backend src/services/invoiceOcr.js con Tesseract.js/PDF.js; procesa PDF, JPG y PNG en español e inglés, con límites de 25 páginas por PDF y 20 MB por archivo.


12. Reservas de áreas sociales

src/components/SocialAreasModule.jsx coordina las pestañas y solicitudes. useSocialAreas.js mantiene el estado y la comunicación con la API; ResidentAreaBooking.jsx presenta la reserva del residente; SocialAreasManagement.jsx presenta el formulario y tabla de administración; socialAreasUtils.js comparte formatos y columnas. ADMIN puede previsualizar el calendario en “Vista de reservas”; el formulario y la tabla quedan en “Administrar áreas”. Las reservas desde la previsualización están deshabilitadas para ADMIN. Las fotos se sirven desde public/social-areas y no se guardan en la base de datos.

src/styles/app.css agrega el diseño responsive de la vista de reservas, la tira horizontal de fechas, la cuadrícula de horarios y la barra de confirmación.

public/social-areas/piscina.jpg contiene la foto de piscina tomada de la referencia visual enviada. Es el único archivo de foto de área recibido hasta ahora; para mostrar fotos reales distintas en cada área deben agregarse sus archivos estáticos y asignarlos en el frontend.

src/components/LoginPage.jsx incluye a residentes en la descripción de roles admitidos; el formulario ya autentica por correo y contraseña y dirige al rol RESIDENTE a Áreas sociales.
